# Dose Ledger（束流站剂量记录账本）

束流站剂量记录的成批落盘与前缀封存服务。零第三方依赖，仅需 Python 3.11
标准库；以独立 WAL 帧保证原子成批写入、崩溃截尾恢复、损坏隔离和乐观并发
抢占。封存点把已确认记录的前缀冻结为可引用摘要（规范 Merkle 根 + 记录数
+ 封存标识），并可逐条出具叶值、同级路径与左右方向，外部不导出完整账本
即可独立复算根值。

## API

### `POST /api/batches`

```json
{ "expected_seq": 4, "records": [120, 95, 88] }
```

- `expected_seq`：调用方所见的下一序号（正整数，首个批次为 `1`）。
- `records`：1–32 条整数剂量记录。
- `201`：整帧 `write + fsync` 完成后才应答，帧内记录获得从 `seq` 起的
  连续序号，返回 `{"status":"committed","seq":4,"count":3,"next_seq":7}`。
- `409 stale_sequence`：所见序号已不是最新（并发抢占失败），**不写任何
  字节、不占用任何序号**，响应体带 `current_seq` 供调用方重读。
- `400`：载荷不合法（非整数、空批、超过 32 条、`expected_seq` 非正整数）。
- `503 ledger_poisoned`：WAL 已损坏。

### `GET /api/records?cursor=<seq>&limit=<n>`

按序号升序返回 `seq > cursor` 的记录；`limit` 1–1000（默认 1000）。
响应含 `next_cursor`，以该值为新游标读取下一页；返回空页时即到末尾。

```json
{ "records": [{"seq": 4, "dose": 120}, ...], "next_cursor": 6 }
```

poisoned 时返回 503，绝不返回可能误导的数据。

### `POST /api/seals`

```json
{ "expected_seq": 6 }
```

- `expected_seq`：调用方所见的下一序号（正整数）。封存点固定**当时全部
  已确认记录**构成的前缀（记录数 `count == expected_seq - 1`），与批次
  提交共用同一条追加顺序（见下"WAL 帧格式"），但不占用任何记录序号。
- `201`：整帧 `write + fsync` 完成后才应答，返回
  `{"status":"sealed","seal_id":"s1","count":5,"next_seq":6,"root":<hex>}`；
  此后前缀的内容与根永久固定，随后写入的记录不影响已封存的 s1。
- `409 stale_sequence`：所见序号已不是最新，不写任何字节、不占用封存
  标识；响应体带 `current_seq`。
- `400 empty_prefix`：账本尚无记录（`expected_seq == 1`）时不可封存。
- `400`：载荷不合法（`expected_seq` 非正整数）。
- `503 ledger_poisoned`：WAL 已损坏。

### `GET /api/seals/<seal_id>/proof?seq=<n>`

按封存标识与记录序号取得成员证明。`200` 响应（结果由规范前缀**每次重新
计算**，同一封存点重复查询逐字节相同；从不依赖缓存树对象或 JSON 对象
遍历顺序）：

```json
{
  "seal_id": "s1",
  "seq": 3,
  "dose": 88,
  "count": 6,
  "leaf": "<64 hex 字符>",
  "path": ["<hex>", "<hex>"],
  "direction": ["left", "right"],
  "root": "<64 hex 字符>"
}
```

- `leaf` 是记录的叶值；`path` 为同级哈希，`direction` 为每一步中**当前
  哈希**所处的位置（`"left"` 表示当前哈希是左孩子，同级在右），二者均
  严格**叶到根**排列、等长对齐。
- 审查员仅凭响应中的字段即可独立复算，规则全部固定：

  1. 叶值 = `SHA256(0x00 || [seq,dose] 的紧凑无空白 UTF-8 JSON)`
     （即 `json.dumps([seq,dose], separators=(",", ":"))`）；
  2. 内部节点 = `SHA256(0x01 || left || right)`；
  3. 非满树按 `k = 2**floor(log2(n-1))` 拆分——左子树恒为满二叉树，
     不足部分全部落在右侧（如 6 叶拆成 4 + 2）；
  4. 单记录前缀的根就是其叶值；证明路径为空。
- `404 unknown_seal`：封存标识不存在；`404 record_outside_seal`：序号
  超出该封存点固定的前缀范围；`400`：`seq` 非正整数；`503`：poisoned。
- poisoned 时封存创建与证明查询一律 503，**不返回证明或记录**。

### `GET /healthz`

正常 `200 {"status":"ok","next_seq":N}`；poisoned 时 `503`。

## WAL 帧格式

批次帧与封存帧共用**同一条物理追加流**，物理帧序号 `frame_no` 对两类
帧统一连续编号（封存帧不参与记录序号）。首字节即区分载荷类型：批次帧
载荷是 JSON 数组（`[`），封存帧载荷是 JSON 对象（`{`）。

```
+----------+----------+----------+----------------+--------+
| magic 8B | frame_no | length   | canonical JSON | SHA256 |
| DSL1WAL\n|  8B u64  | 8B u64   |  紧凑无空白    |  32B   |
+----------+----------+----------+----------------+--------+
```

- 摘要覆盖 **magic + frame_no + length + payload**，尾标 32 字节。
- 批次载荷为整数数组的规范 JSON（`separators=(",", ":")`、UTF-8、保留
  记录在批内顺序）。
- 封存载荷为键集合固定的对象
  `{"id":"s1","count":5,"root":"<64 hex 小写>"}`；键顺序在写出时固定，
  恢复时按 JSON 对象解析（绝不信任对象遍历顺序）并逐字段复核。
- 每帧一次 `write`，随后 `flush + fsync`（并尽力 fsync 父目录）；应答
  发生在持久化之后，因此不存在"应答了但没了"的批次或封存点。

## 恢复与 poisoned 语义

启动时顺序扫描 WAL：

- **唯一允许自动修复的情况**：物理文件末端的不完整帧（帧头写了一半、
  载荷写了一半，或末帧缺尾标字节）——它只可能是崩溃中断的那次追加，
  扫描器将文件**物理截尾**到最后一个完整帧边界（fsync），然后从完整
  帧重建连续序号。
- **以下情况一律令账本进入 poisoned**：完整帧 SHA-256 校验失败、魔数
  错误、长度字段非法（0 或超大且其后仍有帧标记 → 中部结构损坏）、
  帧序号断号/重号（两类帧统一计数）、批次载荷不是 1–32 条整数、
  封存载荷形状/键集合/类型非法、封存标识与其追加位置不符、封存声明的
  记录数超过其之前实际存在的记录。poisoned 后禁止追加、禁止封存、禁止
  返回任何记录或证明、healthz 为 503，且不改动现场文件。

**封存根复核**：每个完整封存帧在扫描时都要从其物理位置之前的批次帧
重建该前缀，按固定规则（见 `/api/seals/<id>/proof`）重新计算 Merkle 根；
任何已完整封存帧与重建根不符——即使该帧自身 SHA-256 合法——都进入
poisoned。因此伪造根、改数记录后保持帧摘要自洽等篡改均无法通过重启。

长度字段损坏的判定：若某帧声明的边界越过 EOF，但在其"缺失区间"内仍能
找到后续帧魔数（整数 JSON 载荷中不可能出现该魔数），说明是中部损坏而非
截尾，必须 poisoned，避免误删其后的已确认帧。

## 并发

进程内一把互斥锁 + `expected_seq` 比较。批次提交会推进序号：同一所见
序号并发提交时恰好一个成功（201），其余全部 409 且在触碰 WAL 之前就
返回——败者零字节、不占序号。封存不推进记录序号：对同一未变前缀的并发
封存各自成功并获得不同封存标识（根相同，均为该前缀的固定摘要）；一旦
并发批次先把序号推进，随后的封存即 409，且不写任何字节。

## 运行

```bash
docker compose up -d --build ledger
# 自定义宿主端口：
LEDGER_HOST_PORT=18080 docker compose up -d ledger
curl -s localhost:8080/healthz
```

数据在命名卷 `ledger-data`（容器内 `/data/wal.bin`）。
也可脱离容器直接运行：`LEDGER_WAL_PATH=./wal.bin python3 -m app.server`。

## 验证（compose 的 verify 服务）

```bash
docker compose run --rm verify
```

单次执行，退出码即结论，依次完成：

1. **构建检查** — `compileall` 字节码编译全部源码/测试/脚本；
2. **代码测试** — 67 个 `unittest` 用例（帧编码、截尾恢复、损坏隔离、
   并发抢占、游标分页、HTTP 503，以及规范 Merkle 根/叶到根证明、封存帧
   持久化、重启根复核伪造隔离、封存证明 HTTP 往返）；
3. **HTTP 冒烟** — `tests/e2e_smoke.py` 驱动真实服务子进程证明：
   - 写入途中 `os._exit` 杀死写入进程 → 重启物理截去半帧、序号连续重建；
   - 翻转完整帧内字节 → 重启后 health/读/写全部 503（poisoned 隔离）；
   - 16 客户端同序号 HTTP 并发 → 恰 1 个 201、15 个 409，WAL 精确增长
     一个帧（败者不留字节、不占序号）；
   - 封存非满前缀（10 条记录跨 4 批）→ 10 个序号的证明全部由独立折叠
     复算恢复已返回根；重复查询逐字节相同；重启后证明不变；半写入封存帧
     被截尾；篡改已封存前缀的完整批次帧 → 封存/证明/健康全部 503；
   - 并对 compose 中运行中的 ledger 容器再做一次 HTTP 提交+封存+证明冒烟。

本地（无 Docker）可直接运行：`sh scripts/verify.sh`（退出码为 0 即通过）。
