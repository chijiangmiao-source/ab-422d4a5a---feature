# Dose Ledger（束流站剂量记录账本）

束流站剂量记录的成批落盘与前缀封存服务。零第三方依赖，仅需 Python 3.11
标准库；以独立 WAL 帧保证原子成批写入、崩溃截尾恢复、损坏隔离和乐观并发
抢占；以规范 Merkle 树把已确认前缀封存为可引用摘要，并提供可独立复算的
包含证明（无需导出完整账本）。

## API

### `POST /api/batches`

```json
{ "expected_seq": 4, "records": [120, 95, 88] }
```

- `expected_seq`：调用方所见的下一序号（正整数，首个批次为 `1`）。
- `records`：1–32 条整数剂量记录。
- `201`：整帧 `write + fsync` 完成后才应答，帧内记录获得从 `seq` 起的
  连续序号，返回 `{"status":"committed","seq":4,"count":3,"next_seq":7}`。
- `409 stale_sequence`：所见序号已不是最新（并发抢占失败），**不写任何
  字节、不占用任何序号**，响应体带 `current_seq` 供调用方重读。
- `400`：载荷不合法（非整数、空批、超过 32 条、`expected_seq` 非正整数）。
- `503 ledger_poisoned`：WAL 已损坏。

### `POST /api/seals`

```json
{ "expected_seq": 6 }
```

外部审查员以其**所见下一序号**创建封存点：服务在同一追加顺序中固定当时
全部已确认记录（序号 `1..expected_seq-1`）的规范 Merkle 根、记录数与
封存标识，封存帧与批次帧共用同一条 WAL、同一个严格递增帧序号，**整帧
`write + fsync` 完成后才返回**：

```json
{"status":"sealed","seal_id":"<32 hex>","count":5,
 "root":"<64 hex>","seq":6}
```

- `seal_id` 即根前 16 字节的十六进制（32 字符），根定了它就定了。
- `409 stale_sequence`：封存点所见序号过期（其间有新批次追加），不写帧。
- `400`：`expected_seq` 非正整数，或前缀为空（尚无已确认记录）。
- `503`：账本 poisoned。封存不占用任何记录序号；封存同一前缀是**幂等**的
  （前缀唯一决定 count/root/seal_id，多个审查员以同一所见序号并发封存、或
  调用方重试，都返回同一封存点且只落一个封存帧）；旧封存点永久可引用，
  其后追加的记录不属于该封存点。所见序号过期（前缀已增长）则返回 409。

### `GET /api/proofs?seal_id=<hex>&seq=<n>`

按封存标识与记录序号取得叶值、同级路径及左右方向：

```json
{"seal_id":"...","seq":3,"dose":30,"leaf":"<64 hex>","count":5,
 "root":"<64 hex>","directions":"RL",
 "siblings":["<64 hex>", "<64 hex>"]}
```

- 调用方仅用返回数据即可独立复算根：从 `leaf` 起按 `directions` 自底向上
  折叠 `siblings`，结果必须等于 `root`。方向字符命名**同级节点**的位置：
  `L` = 同级为左孩子（证明节点在右），`R` = 同级为右孩子（证明节点在左）。
- 仅覆盖封存点内记录：`seq > count` 或封存标识未知返回 `404`；`503` 时
  不返回任何证明或记录。重复查询同一封存点/序号返回字节相同的证明。

### `GET /api/records?cursor=<seq>&limit=<n>`

按序号升序返回 `seq > cursor` 的记录；`limit` 1–1000（默认 1000）。
响应含 `next_cursor`，以该值为新游标读取下一页；返回空页时即到末尾。

```json
{ "records": [{"seq": 4, "dose": 120}, ...], "next_cursor": 6 }
```

poisoned 时返回 503，绝不返回可能误导的数据。

### `GET /healthz`

正常 `200 {"status":"ok","next_seq":N}`；poisoned 时 `503`。

## 规范 Merkle 方案（外部复算契约）

所有规则固定在 `app/merkle.py`，不依赖 JSON 对象遍历顺序或临时内存状态：

- **叶域分隔**：`leaf = SHA256(0x00 || canonical_record)`，其中
  `canonical_record = {"dose":<int>,"seq":<int>}` 的紧凑 JSON
  （`separators=(",", ":")`、键按字典序、UTF-8，即 `{"dose":..,"seq":..}`）。
- **内部域分隔**：`inner = SHA256(0x01 || left || right)`，左右均为 32 字节。
- **非满树拆分**：某层节点数为奇数时，**最后一个节点原样上提**（不复制、
  不重哈希），仅对前面偶数个按下标固定顺序两两配对；配对恒为左 then 右。
  因此 5 个叶时第 5 个叶在第一层无同级步骤，直接与四叶子树根配对。
- **空前缀**根固定为 `SHA256(0x01)`（封存要求前缀非空，故不会经 API 出现）。
- **证明路径顺序**：自叶向根固定排列，每步含一个同级摘要与一个方向；
  被原样上提的层不产生步骤。单记录树路径为空，叶即根。

## WAL 帧格式

两类帧共用同一条物理日志、同一个严格递增的 8 字节帧序号：

```
+-----------+----------+----------+----------------+--------+
| magic 8B  | frame_no | length   | canonical JSON | SHA256 |
| DSL1WAL\n |  8B u64  | 8B u64   |  紧凑无空白    |  32B   |
| DSL1SEAL  |          |          |                |        |
+-----------+----------+----------+----------------+--------+
```

- `DSL1WAL\n` 为批次帧，载荷是剂量整数的 JSON 列表；`DSL1SEAL` 为封存帧，
  载荷是键序固定的
  `{"count":N,"root":"<64 hex>","seal_id":"<32 hex>"}`。
- 摘要覆盖 **magic + frame_no + length + payload**，尾标 32 字节。
- 两个魔数都不可能出现在 JSON 载荷中。
- 每帧一次 `write`，随后 `flush + fsync`（并尽力 fsync 父目录）；应答
  发生在持久化之后，因此不存在"应答了但没了"的批次或封存点。

## 恢复与 poisoned 语义

启动时顺序扫描 WAL：

- **唯一允许自动修复的情况**：物理文件末端的不完整帧（帧头写了一半、
  载荷写了一半，或末帧缺尾标字节，批次帧/封存帧皆然）——它只可能是崩溃
  中断的那次追加，扫描器将文件**物理截尾**到最后一个完整帧边界
  （fsync），然后从完整帧重建连续序号与封存点。
- **以下情况一律令账本进入 poisoned**：完整帧 SHA-256 校验失败、魔数
  错误、长度字段非法（0 或超大且其后仍有帧标记 → 中部结构损坏）、
  帧序号断号/重号（批次帧与封存帧共用序号空间）、批次载荷不是 1–32 条
  整数、封存载荷非法，以及——**封存帧的 `count` 与重建记录数不符，或其
  Merkle 根不能由其之前的记录前缀复算得到，或 `seal_id` 不派生自该根**。
  即持久化的根从不被信任：重启时从 WAL 重建并逐个复核封存点前缀根。
  poisoned 后禁止追加、禁止返回任何记录与证明、healthz 为 503，且不改动
  现场文件。

长度字段损坏的判定：若某帧声明的边界越过 EOF，但在其"缺失区间"内仍能
找到后续帧魔数（两类魔数都会检查；整数 JSON 载荷中不可能出现它们），
说明是中部损坏而非截尾，必须 poisoned，避免误删其后的已确认帧。

## 并发

进程内一把互斥锁 + `expected_seq` 比较：同一所见序号并发提交批次或封存
点时恰好一个成功，其余在触碰 WAL 之前就返回 409——败者零字节、不占序号。

## 运行

```bash
docker compose up -d --build ledger
# 自定义宿主端口：
LEDGER_HOST_PORT=18080 docker compose up -d ledger
curl -s localhost:8080/healthz
```

数据在命名卷 `ledger-data`（容器内 `/data/wal.bin`）。
也可脱离容器直接运行：`LEDGER_WAL_PATH=./wal.bin python3 -m app.server`。

## 验证（compose 的 verify 服务）

```bash
docker compose run --rm verify
```

单次执行，退出码即结论，依次完成：

1. **构建检查** — `compileall` 字节码编译全部源码/测试/脚本；
2. **代码测试** — `unittest` 用例（帧编码、封存帧与交错帧序号、Merkle
   域分隔/非满树向量、包含证明复算、截尾恢复、损坏隔离、封存根重启复核、
   并发抢占、游标分页、HTTP 4xx/503）；
3. **HTTP 冒烟** — `tests/e2e_smoke.py` 驱动真实服务子进程证明：
   - 写入途中 `os._exit` 杀死写入进程 → 重启物理截去半帧、序号连续重建；
   - 翻转完整帧内字节 → 重启后 health/读/写全部 503（poisoned 隔离）；
   - 16 客户端同序号 HTTP 并发 → 恰 1 个 201、15 个 409，WAL 精确增长
     一个帧（败者不留字节、不占序号）；
   - 封存 5 条前缀 → 每条证明仅用返回 JSON 独立折叠回所返回根、叶编码
     符合规范、重复查询字节相同、重启后同一证明仍可复算；构造一个帧
     SHA 合法但根与重建前缀不符的封存帧 → 重启即 poisoned、不返回证明；
   - 并对 compose 中运行中的 ledger 容器再做一次 HTTP 提交+回读+封存
     证明冒烟。

本地（无 Docker）可直接运行：`sh scripts/verify.sh`（退出码为 0 即通过）。
